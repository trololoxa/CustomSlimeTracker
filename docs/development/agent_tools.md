# Работа агента с проектом

Эта страница описывает постановку и приёмку задач в SlimeTracker. Общие ограничения
в [AGENTS.md](../../AGENTS.md); выбор проверок — в [test map](test_map.md).
Настройки модели, launcher, permissions, память сессии и служебные файлы агента
принадлежат его внешнему комплекту. Этот проект не устанавливает их и не утверждает,
что конкретный локальный агент уже прошёл runtime-приёмку.

## Начало ограниченной задачи

В задании нужны одна цель, ожидаемое поведение, фактический checkout и база,
существующие изменения, разрешённая область правок, существенные инварианты,
проверки и критерии завершения. При отсутствии Git commit обозначается unknown;
имя архива и старый отчёт не заменяют идентичность исходников.

Перед правкой сверьте `git status --short`, HEAD и diff, если Git доступен.
Разные Windows/WSL/agent checkouts не считаются одинаковыми по имени папки.
Новый worktree из HEAD не содержит незакоммиченных изменений родительской копии.
Не делайте reset/clean, commit или синхронизацию ради удобства без основания в задаче.
Полный Windows/WSL workflow использует существующий [dev_verify](cross_platform_verification.md).

## Как читать при небольшом контексте

1. Найдите владельца в [module inventory](../architecture/module_inventory.md)
   или строку изменяемой подсистемы в [test map](test_map.md).
2. Через `rg` найдите символ; прочитайте его декларацию, полную реализацию,
   используемое состояние и существенных callers. Большой файл читайте по функциям,
   не только по найденным строкам. В `.hpp` часто только API, поведение — в `.cpp`.
3. Прочитайте существующий тест/fixture и нужные разделы контракта. Для frames/math
   нужен [coordinate frames](../architecture/coordinate_frames.md); для состояния —
   соответствующая часть [ownership](../architecture/ownership.md); для приёмки —
   [testing](testing.md). Не загружайте все страницы заранее.
4. Коротко зафиксируйте изменяемое поведение, сохраняемые условия и проверки.
   Затем выполните правку и проверку без запроса подтверждения каждого локального шага.

Ограничение области правок не запрещает читать нужные зависимости. Если изменение
требует выхода за разрешённую область, объясните это; не обходите границу скрытой
правкой. Недостающий контекст сначала найдите в файлах. Если обязательный источник
недоступен, сообщите BLOCKED для соответствующей части задачи.

Текущий код доказывает существующее поведение, а задание и действующие контракты
определяют требуемое. При расхождении укажите конкретное место: не объявляйте код
правильным только потому, что он уже существует. Старый roadmap не заменяет контракт.

## Команды и выбор проверок

Используйте [session](session.md) только для нужной среды и [runners](runners.md)
для синтаксиса выбора/отчётов. Проверки Python policies запускаются через
`check_all.py --check`, native C++ — через `run_standalone_tests.py --test`.
Точные ID доступны через их `--list-checks` / `--list-tests` без компиляции.
Строка test map — начальный набор; при изменении контракта добавьте затронутые связи.

Синтаксис PowerShell нельзя вставлять в Bash. `$TrackerPython` и другие локальные
переменные из session.md относятся к конкретной PowerShell-сессии. В новом процессе
нужно задать их явно или использовать проверенные абсолютные пути. Наличие `CXX`
в окружении не создаёт PowerShell-переменную `$TrackerCxx`.

Для документации достаточно её проверки; для host tools — затронутых tooling tests.
Матрица в [device guide](device_smoke.md#hardwareruntime-test-budget) определяет,
когда нужны target build, hardware smoke или отдельный timing/persistence тест.
Не запускайте full gate, doctor или аппаратный static capture после каждой правки.
Обязательный, но недоступный вид проверки остаётся непроверенным, а не PASS.

## Возобновление и приёмка

После сжатия контекста или перезапуска восстановите цель, базу, существовавшие правки,
инварианты и следующий шаг из задания/сохранённого состояния внешнего агента.
Сверьте их с реальными файлами и отчётами. Не повторяйте потенциально выполненные
аппаратные действия или активную сборку только потому, что их нет в кратком пересказе.

Сначала читайте `summary.json`, затем raw log нужной ошибки. Полные логи сохраняются
на диске; короткая выдержка может не содержать причину из середины файла. После
изменения причины повторите затронутую проверку, сохранив исходный FAIL.
Старый PASS не относится автоматически к новому diff; новые релевантные правки
после проверки требуют её повторения. Текст модели и exit агента не заменяют gate.

Перед передачей результата просмотрите весь итоговый diff на побочные изменения.
Передайте базу/dirty, изменённые файлы и причину, реальные команды/exit codes,
scope и пути к evidence, непроверенные условия и следующий шаг. Пригодность
результата определяется этими доказательствами и review, а не длиной рассуждений.
Не объявляйте известные ограничения из [status](../status.md) исправленными этим
заданием, если оно их не меняло и не проверяло.

Обычные результаты задачи оформляются в передаваемом diff и verification artifacts,
не новой patch-number страницей в docs. Место служебных записей определяет внешний
агентный комплект. Не меняйте `.gitignore` или правила clean/source identity ради
его приёмки: неигнорируемые untracked-файлы учитываются в идентичности сборки.

## Дополнительные инструменты

Для работы достаточно доступных поиска, чтения, редактирования и проектных runners.
Навигация clangd/compile_commands при необходимости описана в [test map](test_map.md).
Наличие файла базы компиляции не доказывает успешную сборку; host и target используют
разные flags, stubs и пути. Новые skills, MCP, индексаторы и смена модели не являются
обязательным шагом каждого патча. Их полезность оценивается отдельно на одинаковой
задаче и базе по корректности, проверкам, лишним чтениям/повторам и времени.
План отдельного экзамена агента остаётся в [roadmap](../roadmap.md).
